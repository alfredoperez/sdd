SDD Living-Spec Model

Design brief for spec 022 — configurable-spec-location · backed by ADR 0002 · 2026-05-23

The model at a glance

A domain's living spec is a tiered file set that can live centrally in .specs/ or colocated next to the code. A "tree" of specs is just several domains whose paths nest — no special nesting type.

# colocated tree — emergent from paths, registered in .sdd.json src/checkout/ ├─ checkout.spec.md parent · high-level rules + diagrams (overview) ├─ cart/ │ ├─ cart.spec.md leaf · detailed requirements [hot] │ ├─ cart.arch.md architecture + diagrams [cold] │ └─ cart.coverage.md R### → tests (shift-left) [test] └─ payment/ └─ payment.spec.md leaf · detailed requirements [hot]
hot — always loaded cold — on demand (plan/deep change) test — verify / conformance leaf = primary context

Tiered file set (per domain)

hot · requirements

<d>.spec.md

The requirements. Loaded whenever the domain is in scope. Wired in PR1.

cold · architecture

<d>.arch.md

Diagrams + deep explanation. Loaded only to understand/modify architecture. Reserved in PR1, consumed later.

test · coverage

<d>.coverage.md

Maps each R### to its test(s) across files/types. On-ramp to PF-1 conformance. Reserved in PR1.

Resolver: read-all, write-most-specific

changed files

e.g. an edit under src/checkout/cart/

discover (union)

.sdd.json domains ∪ .specs/*/spec.md, ordered most-specific first

read → all

load cart (leaf, primary) and checkout (frame)

write → most-specific

CP3 sync targets cart only — unless a <!-- domain: --> marker says otherwise

One implementation: lib/scripts/resolve-spec-paths.py (+ tests/evals). The four skills call it instead of re-interpreting prose → zero resolver drift.

Decisions locked (this interview)

2
Tree = flat set of domains, emergent from nested paths. No parent/child primitive.Reuses union discovery; pure config, no migration to go finer later.
3
Resolver is a tested script, not prose.Pure & deterministic → eval-able; removes drift across 4 skills (the plan's #1 risk).
4
Read-all / write-most-specific.Rich context on read; precise writes so a requirement isn't duplicated up the tree.
5
Open specFormat → spec-<name>.md, fallback generic.Don't constrain to component/endpoint; teams add feature/service/page by dropping a template.
6
Tiered files (spec / arch / coverage), reserve-now-implement-later.Keeps default context lean; arch & coverage are first-class but on-demand.
7
Incremental, registry-driven adoption.No whole-repo pass; spec the area you're touching; the .sdd.json domains map grows over time.

follow-ups

  • Adoption wizard (extends /sdd:init): area-at-a-time, AI-drafts leaf specs, appends to registry
  • Interview/grill step: the loop that produced this brief — emits an ADR as output
  • Per-file/per-component specs (only if asked for)
